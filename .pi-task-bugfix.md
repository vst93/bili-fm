# Bug Fix Task: Window Drag + Image Display

## Bug 1: Window title bar not draggable

### Root cause
The app uses `--wails-draggable: drag` CSS property (Wails-specific) for window dragging. Tauri v2 does NOT support this property. Tauri v2 uses `data-tauri-drag-region` HTML attribute instead.

### Fix needed
1. In `src/components/titleBar.tsx`: Add `data-tauri-drag-region` attribute to the `.app-title-bar` div element. Keep it on the container but NOT on buttons/icons inside (they need `data-tauri-drag-region="false"` or just not have the attribute).

2. In `src/styles/globals.css`: Remove all `--wails-draggable` CSS properties. There are 3 occurrences:
   - `.app-title-bar { --wails-draggable: drag; ... }` (line ~94)
   - `img { --wails-draggable: no-drag }` (line ~120) 
   - Any other `--wails-draggable` references

3. In `src/components/titleBar.tsx`: Remove all inline `style={{ ['--wails-draggable' as string]: 'no-drag' }}` from buttons. They are not needed in Tauri - only elements WITH `data-tauri-drag-region` are draggable, everything else is automatically non-draggable.

4. Also check `src/pages/index.tsx` for any `--wails-draggable` references and remove them.

5. Check capabilities: `src-tauri/capabilities/default.json` must have `"core:window:allow-start-dragging"` permission. It should already be there from Round 2, but verify.

## Bug 2: Images not displaying (avatars, covers, etc.)

### Root cause
The `graftingImage()` function in `src/utils/string.tsx` returns `/image-proxy?url=<encoded_url>` - a relative path. In Wails, this worked because Wails' asset server middleware intercepted `/image-proxy` requests. 

In Tauri, the image proxy server runs on `http://127.0.0.1:4654`, but `graftingImage()` doesn't prepend the host. So `/image-proxy?url=xxx` resolves to the app's own origin (which doesn't serve this route) -> 404.

Additionally, `proxyImg.tsx` tries to extract the original URL from proxy URLs and call `invoke("fetch_image")`. This works when the input is `http://127.0.0.1:4654/image-proxy?url=xxx` (can parse with `new URL()`), but FAILS when the input is `/image-proxy?url=xxx` (relative path - `new URL()` throws, falls to catch, uses `src` as-is which is the broken relative path).

### Fix needed
1. In `src/utils/string.tsx`: Change `graftingImage()` to return the full proxy URL with host:
```typescript
export const graftingImage = (img: string) => {
  if (img) {
    return `http://127.0.0.1:4654/image-proxy?url=${encodeURIComponent(img)}`;
  }
  return img;
};
```

2. In `src/config/index.ts`: The `proxyImagePort` config is no longer needed for the frontend (the port is hardcoded in Rust). But keep it for reference, or remove it if unused. Check if `setProxyImagePort` is called anywhere - if not, remove both.

3. In `src/components/proxyImg.tsx`: The current logic should work once `graftingImage` returns full URLs, because `new URL(src)` will parse `http://127.0.0.1:4654/image-proxy?url=xxx` correctly, extract the `url` param, and call `invoke("fetch_image")`. But add a fallback: if `new URL()` throws (relative URL), try extracting `url` param manually:
```typescript
let originalUrl = src;
try {
  const u = new URL(src);
  const urlParam = u.searchParams.get("url");
  if (urlParam) originalUrl = urlParam;
} catch {
  // Relative URL like /image-proxy?url=xxx - extract manually
  const match = src.match(/[?&]url=([^&]+)/);
  if (match) originalUrl = decodeURIComponent(match[1]);
}
```

4. In `src-tauri/tauri.conf.json`: Verify the CSP allows `img-src` from `http://127.0.0.1:4654`. Current CSP already has this, but double-check.
